I am going to give you the URL of a live website. Your job is not to clone it. Your job is to reverse-engineer what the product actually does, understand why customers pay for it, identify the complete functional system behind the experience, and then rebuild that underlying concept as a new, original, more capable, production-quality product. Reference site: https://stagetimer.io The function may be inherited. The design may not. Nothing you ship should visually resemble the reference site closely enough to be mistaken for it. Do not copy: * branding * product name * typography * colors * layout * icons * illustrations * copywriting * interface composition * visual hierarchy * motion language * onboarding language * marketing language * trade dress Take the product logic. Reject the surface expression. Then improve the product. The reference site should be treated as a minimum competitive benchmark, not as a feature limit. The finished application should feel like a new company asked: “What should a world-class live timing and run-of-show platform be in 2026 if we designed it from first principles?” ⸻ 1. RESEARCH FIRST Before writing the product, inspect the current live StageTimer product thoroughly. Do not rely on assumptions. Research: * homepage * product pages * pricing * documentation * public demo if available * supported timer modes * room structure * controller workflow * viewer/display workflow * agenda/run-of-show functionality * messages * alerts * chimes * remote control * sharing * branding/customization * embeds * integrations * mobile behavior * desktop behavior * account model * paid tiers * limits * event licensing * enterprise features Also inspect strong adjacent competitors where useful. Potential categories include: * event countdown timers * conference stage timers * presentation timers * livestream timers * production run-of-show tools * church service timers * podcast timing tools * meeting timers * backstage cue systems Do not copy their design. Use them to identify the true competitive standard. ⸻ 2. IDENTIFY THE CUSTOMER PROBLEM The product should solve a clear high-value problem: “I need multiple people to stay synchronized around time, cues, messages, and the running order of a live event.” Core use cases include: * conferences * panels * live events * livestreams * stage productions * corporate meetings * church services * podcasts * webinars * broadcasts * ceremonies * workshops * presentations * classrooms * production teams The product must work equally well for: * the person controlling time * the speaker/presenter viewing time * backstage staff * producers * moderators * technical crew * remote participants ⸻ 3. CORE PRODUCT MODEL The essential workflow should be: Create Event → Build Run of Show → Start Session → Share Displays → Control Live → Adjust in Real Time → Review / Reuse The product should be built around persistent Events, not disposable timers alone. An Event should be able to contain: * agenda items * timed segments * speakers * labels * start times * durations * countdowns * count-ups * messages * cues * alerts * notes * display assignments * operator notes * event state * live progress ⸻ 4. REAL-TIME SYNCHRONIZATION This is foundational. Multiple devices must remain synchronized in real time. Examples: Operator laptop changes timer → speaker display updates immediately. Operator pauses timer → every connected display pauses. Operator sends message → assigned displays receive it instantly. Operator switches agenda item → stage display changes immediately. Use a production-capable real-time architecture. Appropriate technologies may include: * Supabase Realtime * WebSockets * server-sent events * another production-ready real-time system The architecture must handle: * reconnects * temporary network loss * duplicate events * clock drift * stale state * browser refresh * multiple operators * multiple displays * mobile devices Avoid designs where each client independently counts time and slowly drifts apart. Use server-authoritative or synchronized clock logic where appropriate. ⸻ 5. EVENTS / ROOMS Users should be able to create an event or room quickly. Each should include: * name * date * optional venue * timezone * status * owner * collaborators where supported * event settings Generate secure shareable URLs for: * operator/control view * stage display * speaker display * audience display where relevant Public displays should not automatically grant editing permissions. ⸻ 6. RUN OF SHOW Build a high-quality run-of-show system. Users should be able to create agenda items such as: * opening * speaker * panel * break * transition * video * performance * Q&A * closing * custom segment Each item can include: * title * speaker/person * planned duration * scheduled start * scheduled end * notes * display label * warning thresholds * overrun behavior * optional cue Support: * drag-and-drop reorder * duplicate * delete * insert * bulk import * CSV import/export * copy from previous event * reusable templates The run-of-show should be easy enough for a novice yet powerful enough for professional event staff. ⸻ 7. LIVE CONTROL CONSOLE The live operator console is the heart of the product. It must feel extremely reliable and calm under pressure. Support: * start * pause * resume * reset * add time * subtract time * skip * previous item * next item * restart item * manual timer entry * jump to agenda item * send message * trigger alert * acknowledge cue Large critical controls must be hard to misclick. Destructive or disruptive actions should have sensible safeguards without slowing the operator down. Keyboard shortcuts should exist for professional users. ⸻ 8. TIMER MODES Support multiple timer types: Countdown Example: 10:00 → 00:00 Count Up 00:00 → elapsed time Time of Day Current local event time. Scheduled Countdown Countdown until a specific clock time. Overtime When countdown reaches zero, continue displaying elapsed overtime. Stopwatch Manual elapsed timer. Support negative/overtime states elegantly. ⸻ 9. WARNING STATES Timers should visually communicate status without requiring people to read small numbers constantly. Allow configurable warning thresholds. Example: Normal → warning at 2 minutes → urgent at 30 seconds → overtime at zero Do not rely solely on color. Use combinations of: * color * motion * text * icons * size changes * optional sound Support accessibility needs including color blindness. ⸻ 10. DISPLAY MODES Create multiple polished display experiences. Speaker Display Prioritize: * huge timer * current segment * next segment where useful * private operator message * minimal distraction Stage Display Suitable for: * confidence monitors * backstage monitors * green rooms * production booths May show: * timer * current speaker * upcoming item * cues * operator messages Audience Display Optional display for public-facing timing such as: * breaks * session start * intermission * countdown to livestream Public-facing displays should be visually refined. ⸻ 11. DISPLAY CUSTOMIZATION Allow appropriate customization without turning the application into Canva. Support: * logo * background color * text color * typography choices * timer scale * layout density * event name * optional background image * brand accent Premium customization can be monetized. Do not create a giant template marketplace. ⸻ 12. OPERATOR MESSAGES Operators should be able to send real-time messages. Examples: 2 MINUTES WRAP UP SLOW DOWN MIC CHECK PLEASE WAIT Q&A NEXT Support: * preset messages * custom messages * targeting specific displays * message expiration * clear * urgent priority Speaker messages should be obvious without obscuring the timer unnecessarily. ⸻ 13. CUES Introduce lightweight production cues. Examples: * GO * HOLD * STANDBY * MIC LIVE * VIDEO READY * LIGHTS * NEXT SPEAKER * BREAK Allow operators to trigger cues independently of the timer. This should remain simple enough for non-technical users. ⸻ 14. SOUND / CHIMES Allow optional audible alerts. Examples: * warning * timer complete * overtime * next item * custom cue Controls must clearly indicate when audio is enabled. Browsers’ autoplay restrictions must be handled honestly. Do not claim sound will fire automatically where the browser requires user interaction. ⸻ 15. AI RUN-OF-SHOW IMPORTER This should become one of the new product’s differentiators. Allow a user to provide: * pasted schedule * plain text * agenda * CSV * PDF where supported * document where supported Then use AI to propose a structured run of show. Example input: “Welcome 9:00–9:10 Sarah keynote 9:10–9:40 Panel 9:45–10:30 Break 10:30–10:45” The system should produce editable agenda items. The AI must never silently publish or start an event. Show the interpreted schedule before applying it. Allow users to correct mistakes. ⸻ 16. NATURAL-LANGUAGE EVENT CONTROL Explore an optional natural-language command layer. Examples: “Give Sarah five more minutes.” “Move the panel after lunch.” “Make every keynote warning happen at two minutes.” “Send wrap up to stage left.” “Add a fifteen-minute break after this session.” These commands should map to visible deterministic operations. The user should be able to inspect and undo changes. Do not replace reliable controls with a chatbot. Language should accelerate control, not obscure it. ⸻ 17. SCHEDULE INTELLIGENCE Add useful timing intelligence. Examples: * event currently 12 minutes behind schedule * next break would recover 5 minutes * keynote overran by 7 minutes * remaining event duration * projected finish time * total planned vs actual time Do not fabricate predictive certainty. Use clear deterministic timing math. ⸻ 18. AUTO-CATCH-UP MODE Design an optional tool to help recover lost time. Example: Event is 14 minutes behind. User chooses: Recover 10 minutes before lunch. Product can propose reductions across selected flexible segments. Example: * Panel: -3 min * Break: -2 min * Q&A: -5 min Never modify agenda durations automatically without confirmation. ⸻ 19. MULTI-DISPLAY MANAGEMENT Professional events may have many displays. Create a display-management view showing: * display name * connection status * assigned layout * last heartbeat * current content * online/offline state Allow naming displays such as: * Main Stage * Speaker Confidence * Backstage * Green Room * Stream Booth * Stage Left * Stage Right This is highly valuable for professional users. ⸻ 20. DEVICE PAIRING Make connecting displays extremely easy. Support mechanisms such as: * share link * short code * QR code Example: Open display URL on stage monitor → enter six-digit event code → connected. Maintain strict permissions. A display should not become an operator simply because it has the event code. ⸻ 21. EVENT TEMPLATES Allow recurring users to save reusable structures. Examples: * Weekly Church Service * Conference Day * Panel Discussion * Podcast Episode * Webinar * Board Meeting * Livestream * Awards Ceremony Templates should store structure, not private historical content unless explicitly included. ⸻ 22. DUPLICATE / REUSE EVENTS A user should be able to duplicate yesterday’s event or last week’s service in seconds. Support: * duplicate event * reset actual times * preserve agenda * preserve display settings * optionally preserve speakers * regenerate dates This is a strong recurring-use feature. ⸻ 23. COLLABORATION Support sensible collaboration. Potential roles: Owner Full control. Producer Edit agenda and operate live. Operator Live control access. Viewer Read-only dashboard. Display Presentation-only device. Use proper authorization. Never depend only on hiding buttons in the UI. ⸻ 24. AUTHENTICATION Use production-quality authentication. Support: * signup * login * logout * password reset * secure sessions * email verification where appropriate Do not use another platform’s identity system as the customer-facing application account unless explicitly intended. The product needs its own brand/account experience. ⸻ 25. CLOUD PERSISTENCE Persist: * accounts * events * agenda items * templates * display configuration * event status * collaborators * subscription state * usage limits Use strict row-level security or equivalent authorization. Test cross-user data isolation. A customer must never be able to access another customer’s private event. ⸻ 26. HISTORY / POST-EVENT REVIEW After an event, provide useful historical information. Examples: * planned duration * actual duration * overtime * start delay * finish delay * total event variance A simple timeline could show: planned vs actual. This creates additional value beyond the timer itself. ⸻ 27. EXPORTS Allow useful exports: * run of show PDF * CSV * actual timing report * event summary Where useful, include: * planned start * actual start * planned duration * actual duration * variance ⸻ 28. MOBILE EXPERIENCE This application must work extremely well on phones. Operators often control events while standing backstage. Design mobile controls deliberately. Do not merely collapse the desktop interface. Important mobile priorities: * current timer * current segment * next segment * start/pause * add/subtract time * next * message * cue Large touch targets are mandatory. ⸻ 29. TABLET EXPERIENCE Tablets may be ideal operator consoles. Build a polished tablet layout. Do not treat tablet as oversized mobile. ⸻ 30. OFFLINE / NETWORK FAILURE BEHAVIOR Live-event software must remain useful during unreliable connectivity. Design graceful behavior for: * operator briefly losing internet * display reconnecting * browser sleeping * device reload * network switching * temporary backend outage At minimum, provide: * clear connection status * automatic reconnection * last-known state * conflict handling * timer continuity where technically possible Never silently display stale time as if it is live. ⸻ 31. RELIABILITY This product may be used in front of hundreds or thousands of people. Reliability matters more than decorative novelty. Avoid: * unnecessary page transitions * fragile animation * excessive client state * hidden failure conditions * ambiguous button states Core timer operations must be deterministic and testable. ⸻ 32. PERFORMANCE Optimize for: * instant controller response * extremely low display update latency * fast room loading * mobile networks * low CPU overhead * long-running browser sessions Timers should not drift simply because a tab has been open for hours. ⸻ 33. ACCESSIBILITY Support: * keyboard navigation * clear focus * screen-reader labeling * high contrast * scalable text * non-color warning signals * reduced-motion preference Large timer displays should remain legible from significant distance. ⸻ 34. PREMIUM VISUAL DESIGN This must feel like high-end professional production software. It should communicate: * calm * precision * control * trust * speed Avoid: * generic SaaS dashboards * giant gradient blobs * template-looking cards * playful consumer-app clutter * excessive decoration * unnecessary illustrations The timer itself should command the interface. Create a distinctive original visual identity. Do not visually copy StageTimer. ⸻ 35. BRAND Create a new original product identity. Key pages should include: * Home * Product * Use Cases * Pricing * Live Event Timer * Conference Timer * Presentation Timer * Church Timer * Livestream Timer * Run of Show * Login * Signup Each should be genuinely useful, not thin SEO filler. ⸻ 37.
